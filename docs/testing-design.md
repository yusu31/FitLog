## 1. テストの方針

### 1-1. 層と役割

テストは「速くて安い順」に層を重ねる。下の層ほど数が多く、上の層ほど少なく・遅く・壊れやすい。

| 層 | 何を確かめるか | 実際の PostgreSQL | 実行の頻度 |
|----|----------------|-------------------|-----------|
| 単体（unit） | 1つの関数・クラスの判断（勝ち負けの比較・週の境目・入力の範囲） | 使わない | 毎回（数秒） |
| 結合（API + DB） | API を呼んで、DB まで通した結果（制約・冪等・権限・トランザクション） | **使う** | 毎回 |
| 画面部品 | 1つの画面部品の見え方と操作（文字数・ボタンの出し分け・送信待ちの帯の件数） | 使わない（API は偽物） | 毎回 |
| E2E | 本物のブラウザで、画面から API・DB まで通した利用者の流れ | 使う | 毎回（本数を絞る） |
| アクセシビリティ検査 | 画面の読み上げ・コントラストなどの機械で見つかる問題 | 使わない | 毎回（E2E に相乗り） |
| 性能 | 速さの目標を満たすか | 使う | **毎回は回さない**（手動／節目） |

**なぜ結合テストで本物の PostgreSQL を使うのか:** このアプリの大事な約束の多くが DB の制約で守られているため。「休みは1日1件」（部分一意インデックス）・「1人1グループ」（`group_members.user_id` の UNIQUE）・「同じ ID は1件」（`ON CONFLICT DO NOTHING`）・コメント50字（CHECK）は、DB を偽物に差し替えると、確かめたつもりで何も確かめていないことになる。

**偽物（モック）を使ってよい所:** S3 の署名付き URL の発行（本物の AWS に触れない）、Cloudflare Workers AI（F-23。できれば）、時計（日付の固定）。自分の DB は偽物にしない。

### 1-3. テストケースの決め方

[CLAUDE.md](../CLAUDE.md) のとおり、次の3つの技法でケースを導く。

| 技法 | 意味 | このアプリでの使いどころ |
|------|------|--------------------------|
| 同値分割 | 「同じ扱いになる入力」を1つの仲間にまとめ、仲間ごとに1つ試す | 重量が範囲の中／下／上、記録の種類（workout・run・rest） |
| 境界値分析 | 仲間の「境目」の両側を必ず試す（不具合は境目に多い） | 0／0.5／500／500.5、50字／51字、日曜 23:59／月曜 0:00 |
| デシジョンテーブル | 条件の組み合わせと結果を表にして、抜けを見つける | ゴーストの勝ち負け、他グループの見え方、招待を受けたときの結果 |

**ルール:**
1. 境界値は「範囲の中の端」と「範囲の外の隣」の2つを書く（例: 500 は通り、500.5 は 400）
2. 期待結果は features.md／design.md の記述をそのまま使う。**書かれていない振る舞いは、ケースに「未決」と書き、勝手に期待値を決めない**（実装の前に元の文書へ決めを足す）
   - **更新（2026-10-28・ゲートレビュー後）**: 以前「未決」としていた振る舞いは、[design.md の 7章](./design.md#7-細かい取り決めテスト設計の洗い出しで決めたもの)と、2026-10-28 に本人が決めたこと（オフラインの扱い・テストの道具・非機能の測り方・招待の確認。同じ PR で design.md などにも書く）に合わせて、期待値を書き直した。いまも「未決」なのは、8章に残した項目だけ
3. ケースの ID は `T-領域-番号`（例: `T-SET-03`）。テストの名前に入れ、どの表に対応するかを追えるようにする

## 2. テストの道具（**2026-10-28 に確定。API も画面も Vitest。tech-stack.md に書いた**）

tech-stack.md の表には、テストの道具がまだ無い（02-1 ① で足す）。決めた方針は次のとおり。以下の表は、選んだ理由と、選ばなかった案の記録として残す。

- **API（NestJS）= Vitest／画面 = Vitest + Testing Library／E2E = Playwright**（01-7 では API を Jest としたが、02-1 ① で雛形が Vitest と分かり、デコレーターの型情報が効くことを実測で確かめて**決め直した**。理由は tech-stack.md）
- 下の 2-1 の表は、決め直す前の比較の記録として残す。Jest の「気になる所」と Vitest の「要確認」は、実測で解消した

版は 2026-10-28 に `npm view` で確かめた最新版（実装時に固定する。TypeScript 6.0 系・NestJS 12 との組み合わせで動くかは、02-1 の最初の PR で実際に確かめる）。

### 2-1. API（NestJS）の単体・結合テストの実行器

| 候補 | 版 | 良い所 | 気になる所 |
|------|-----|--------|-----------|
| Jest | 30.5.2 | NestJS の公式の説明・雛形が前提にしている（12 系の雛形は 02-1 で確かめる）。情報が多く、初学者が詰まりにくい | TypeScript の変換に ts-jest 等が要り、やや遅い |
| Vitest | 5.0.5 | 速い。画面側と同じ道具にそろえられる | NestJS はデコレーターの型情報（`emitDecoratorMetadata`）に頼るが、Vitest の標準の変換はこれに対応しないと言われている。SWC のプラグインなどの追加が要る見込み（**要確認**） |

**決めた理由（決め直したあと）:** 雛形の既定が Vitest で、`emitDecoratorMetadata` を切ると見本テストが `Cannot read properties of undefined` で落ち、入れると通る（2026-10-28 に実測）。型情報の心配が消えたので、画面と API で道具をそろえる利点（覚えることが減る）を取る。確定の確認項目のうち「NestJS 12 のテストが1本通る」は済み（Drizzle・better-auth は 02-1 ③ の認証で確かめる）。

### 2-2. 画面（Next.js）の部品テスト

| 候補 | 版 | 備考 |
|------|-----|------|
| Vitest + Testing Library（`@testing-library/react` + `user-event`） | 5.0.5 / 16.3.3 / 14.6.8 | 画面部品を「利用者が見える形」で探して操作する。Next.js の公式ドキュメントにも例がある |
| Jest + Testing Library | 30.5.2 | 画面も Jest にそろえる案。画面は Vitest + Testing Library に決めたので採らない（理由: 画面は Next.js と相性がよく速い。API と別の道具になる点は 02-1 ① の確認で見直せる） |

通信の偽物には MSW（Mock Service Worker・3.0.3）が候補。ただし API の型を orval で生成するので、**偽の応答も生成した型に合わせて書く**（型が変わったら偽物がコンパイルで落ちるようにする）。

### 2-3. DB の結合テストの用意のしかた

| 候補 | 版 | 良い所 | 気になる所 |
|------|-----|--------|-----------|
| Testcontainers（`@testcontainers/postgresql`） | 12.2.1 | テストが自分で使い捨ての PostgreSQL を起動・破棄する。手元と CI で同じ動き | Docker が要る。起動に数秒かかる |
| GitHub Actions の `services:`（postgres コンテナ）＋ 手元はローカルの PostgreSQL | - | 設定が少ない。CI が速い | 手元と CI でつなぎ方が違い、「CI でだけ落ちる」原因になりうる |
| Neon のブランチをテスト用に使う | - | 本番と同じ Neon で試せる | 通信と秘密情報が要り、CI が外の事情で落ちる。**採らない方向**（理由: 外部サービスの無料枠・停止の影響をテストが受ける） |

**共通の決まり（仮置き）:** PostgreSQL の版は Neon の版にそろえる。マイグレーションを**本番と同じ手順（drizzle-kit）で**空の DB に流してからテストを始める（スキーマを手で作らない）。テスト間は、ファイルごとに全テーブルを空にして独立させる。

### 2-4. E2E・アクセシビリティ・時計・API 呼び出し

| 用途 | 候補 | 版 | 備考 |
|------|------|-----|------|
| E2E | Playwright（`@playwright/test`） | 1.64.1 | tech-stack.md・screen-design.md が既に前提にしている（**E2E はこれで決定済みの扱い**）。オフライン（`context.setOffline`）・動きを減らす設定（`emulateMedia`）が使える |
| アクセシビリティ | `@axe-core/playwright`（axe-core） | 4.14.0 | E2E の画面を開いたついでに検査する。機械で見つかるのは問題の一部だけなので、読み上げの目視確認は残す |
| API を呼ぶ | supertest | 7.3.1 | NestJS の結合テストで HTTP を直接呼ぶ。候補（Nest の雛形に含まれる見込み） |
| 時計の固定 | 各実行器の偽の時計機能（Jest／Vitest 内蔵）。単独なら `@sinonjs/fake-timers` | 15.4.0 | 下の「時計は注入する」を守れば、道具に依らない |

**時計は注入する（決定）:** 「今」を使う処理（週の判定・未来の時刻の検査・招待の期限・動画の期限）は、`new Date()` を直接呼ばず、`Clock`（今を返す部品）を受け取る形にする。テストでは固定した時計を渡す。道具の偽の時計に頼ると、非同期処理と絡んで不安定になりやすい。

## 3. 主要機能のテストケース

表の見方: 「期待」の数字は features.md／design.md の値。「技法」は 同=同値分割・境=境界値・デ=デシジョンテーブル。層は単=単体／結=結合。

## 4. 実行件数の確認と、テストが本当に効いているかの確認

### 4-1. 0件でも成功になる罠

テストの道具は、**テストが1件も見つからなくても成功（終了コード0）として終わる設定**を持つことがある（設定の書き違いで対象のファイルが空になった、フィルターが全部を除外した、などで起きる）。緑の表示だけを見ると、何も確かめていないのに「通った」と思ってしまう。

**決まり（[CLAUDE.md](../CLAUDE.md) の完了条件）:**
1. テストの完了報告は「実行件数」を書く（例: 単体 142 件・結合 38 件・E2E 6 件、失敗 0、スキップ 0）
2. CI は、道具の機械が読める出力（JSON などの reporter）から**実行件数を取り出して、下限より少なければ落とす**。下限は、今ある件数より少し低い値にして、PR で件数が増えたら引き上げる（仮置き。値は実装を始めてから決める）
3. 「0件でも通す」オプション（Jest の `--passWithNoTests` など）は使わない
4. `.only`（一部だけ実行）の取り残しは CI で落とす。Playwright は設定の `forbidOnly` で止められる。単体・結合・画面は lint の規則で止める候補（02-1 で決める）
5. スキップ（`skip`・`todo`）の件数も出力に出し、増えたら PR のレビューで理由を確かめる

### 4-2. 陽性対照（わざと落として、検出できるかを確かめる）

「陽性対照」は、**わざと壊して、テストがちゃんと赤になるか**を確かめること。赤にならないテストは、書いた本人の期待しか写していない可能性がある。

| いつ | やること |
|------|----------|
| 新しいテストを書いたとき（毎回） | 実装を1か所わざと壊す（境界を `<` から `<=` に変える、条件を消す）→ 赤を見る → 戻して緑にする。PR に「赤を確認した」と1行書く |
| バグを直すとき | 先にそのバグを再現して落ちるテストを書く（Red）→ 直す → 緑（Green） |
| 土台の PR（02-1 の最初） | CI の各ジョブについて、わざと壊した変更で赤になることを1回確かめる（型エラー・lint 違反・失敗するテスト・秘密情報に見える文字列）。必須チェックが本当に merge を止めることも確かめる |
| 重要なテスト（3-7・T-GRP-04・T-OFF-01） | 下の表の壊し方で、必ず赤になることを一度確かめて記録に残す |

| 壊し方 | 赤になるべきテスト |
|--------|---------------------|
| 共通の取得関数から `group_members` の結合を外す | 3-7 の全部 |
| 参加の処理のトランザクションをやめる（数える→追加の間に隙を作る） | T-GRP-04 |
| `ON CONFLICT DO NOTHING` を外す | T-OFF-01・02・06 |
| 部分一意インデックスを外す | 休みの二重（T-REST-06） |
| `local_date` を UTC の日付で出す | T-DATE-01〜03 |
| 動画の期限の比較を `<` から `<=` に変える | T-VID-02 |

自動化はしない（やりすぎ）。手でわざと壊して確かめた内容をテストの PR に書く。変異テスト（コードを自動で壊して検出率を測る道具）は、後で検討する候補（今は決めない）。

## 6. CI の段階

[CLAUDE.md](../CLAUDE.md)「品質の仕組み」のとおり、テストが通らない変更はマージできない運用にする（ブランチ保護の必須チェック）。

### 6-1. 今の状態

`.github/workflows/ci.yml` で動いているのは**秘密情報の検査（gitleaks）だけ**。残りは 02-1 の最初の PR で足す（ci.yml のコメントと同じ）。

### 6-2. 目指す段階

| 順 | ジョブ | 内容 | 動かす時点 | 必須チェック | 目安の時間（仮置き） |
|:---:|--------|------|-----------|:---:|------|
| 1 | 秘密情報の検査 | gitleaks（**動作中**） | PR・main への push | はい | 1分以内 |
| 2 | lint | 書き方の検査 | PR・push | はい | 1〜2分 |
| 3 | 型チェック | TypeScript の型。画面と API の両方。orval の生成物が最新かの確認（生成し直して差分が出たら落とす）を含める | PR・push | はい | 1〜2分 |
| 4 | 単体・画面部品 | 4-1 の件数チェック付き | PR・push | はい | 数分 |
| 5 | 結合 | 本物の PostgreSQL（2-3）。マイグレーションを空の DB に最初から流し、**2回流しても壊れないこと**も確かめる（database-design.md の5章） | PR・push | はい | 数分 |
| 6 | ビルド | Next.js の静的書き出し、NestJS のビルド | PR・push | はい | 数分 |
| 7 | E2E | Playwright（Chromium）で、本数を絞った主要な流れ（登録 → 記録 → ゴースト／オフライン／他グループが見えない） | PR・main への push | **最初は必須にしない** | 5〜10分 |
| - | アクセシビリティ | E2E に相乗り | 7 と同じ | 7 と同じ | - |
| - | 性能 | 回さない（5章） | 手動 | いいえ | - |

**必須にする順番の考え方:** まず 1〜6（速く、揺れにくい）を必須にする。E2E は、遅く・揺れやすいので、安定して数回通ることを確かめてから必須に加える（揺れるテストを必須にすると、無関係な PR が止まって、人が「再実行」を押すのが癖になる。それが一番危ない）。ブランチ保護の設定名（必須チェックのジョブ名）は、ジョブ名を変えると外れるので、変えるときは設定も直す。

**CI が赤のとき:** テストを弱めて通さず、製品のコードを直す（CLAUDE.md）。**揺れるテストを見つけたら**、再実行で隠さず、原因（待ち方・時計・順序の依存）を直す。

**秘密情報:** CI で使う接続先はテスト用の使い捨ての DB だけ。本番の接続文字列・署名鍵を CI に渡さない。テストのために本物の AWS・Neon・Cloudflare に接続しない。

## 7. テストデータの作り方

### 7-1. 種目の一覧

`exercises`（部位つきの一覧・約30種目）は、マイグレーションが**固定の ID** で入れる（database-design.md）。したがって:
- 結合テストは、マイグレーションの結果をそのまま使う（テストが種目を作り直さない）。テストの中では、`ベンチプレス` などを**名前で探さず、固定の ID の定数**で指す（名前が変わってもテストの意味が変わらないように）
- 自分用に追加した種目（`created_by` が入る）は、テストの中で作る
- `body_part` が仮置きなので、部位の個数を数えるテストを書かない（7つと決め打ちしない。列挙値から作る）

### 7-2. 作り方の決まり

| 決まり | 理由 |
|--------|------|
| テストごとに、必要なデータを**テストの中で**作る（共有の大きな初期データに頼らない） | 他のテストが変えても影響されない。何を前提にしたテストか読めば分かる |
| データは「作る関数（ファクトリ）」で作り、1つの値だけ変えられるようにする（例: 記録を作る関数に `localDate` だけ渡す） | テストが短くなり、何を確かめたいかが目立つ |
| 人は固定の名前（例: `member-a1`）で作る。ID は毎回ランダムでよいが、テストの結果は ID に依らない | 3-7 の「グループ A・B・なし」を読みやすく作る |
| ファイルごとに全テーブルを空にする（仮置き。遅ければテストごとのトランザクションの巻き戻しを検討） | テストの順番に依らず同じ結果になる |
| 認証は、better-auth を通してログインしたセッションの Cookie をテスト用に作る関数で用意する（認証を飛ばす裏口を製品コードに足さない） | 「401」と「404」を本物の仕組みで確かめるため。方法は版を固定するときに確かめる |

### 7-3. お試しの前回値（F-11）

対象: F-11

お試しゴースト（例: ベンチプレス 20kg×10）は**記録として保存しない**。確かめること: お試しの値を表示したあとで DB の `workout_sets` が0行のまま（結合）、灰色の「お試し」の札が出る（画面部品）、本物の前回ができたらお試しは出ない（デシジョンテーブルの1行）。

### 7-4. 日付と時計の固定

- 固定の基準は **2026-10-26（月）0:00 日本時間 = 2026-10-25T15:00:00Z**。この週の中の日付（月〜日）と、前後の週を、定数にする
- 「今日の日付」で動くテストを書かない。必ず時計を渡す（2-4）
- E2E は、ブラウザ側の時計も固定する（Playwright の時計の機能が使えるかは版を固定するときに確かめる）。使えない場合は、日付をまたぐ流れを E2E でなく画面部品と結合に任せる
- 曜日は定数に直接書かず、日付から計算させるテストを1本入れる（曜日の対応表の書き間違いを防ぐ）

### 7-5. ファイルの置き場所（仮置き）
