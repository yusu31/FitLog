# 運用設計書

## FitLog

動かし続けるうえでの「ログに何を残すか」「何を見張るか」「困ったときの順番」「データを戻せるか」を定義する。AWS の構成は infrastructure.md、テストは [testing-design.md](./testing-design.md)、非機能の目標は [requirements.md](./requirements.md) の 5 章を正とする。

> **前提:** 少人数（最大5人のグループ）で使う個人開発。常に人が張り付いて見張る前提ではなく、「異常に気づくための粗い網」を無料の範囲で張る。
> **お金の決まり:** 費用が出るものは「**本人確認が必要**」と書き、確認が取れるまで有効にしない（[CLAUDE.md](../CLAUDE.md)）。単価は公式ページで確かめられたものだけ書く。確かめていないものは「未確認」と理由を書く。

## 1. ログ設計

ログの方針（レベルの使い分け・構造化ログ・個人情報を出さない）は [design.md の「ログ」](./design.md#ログ) と [CLAUDE.md](../CLAUDE.md) の「品質の仕組み」が正。ここには**書き写さず**、それに足して決めることだけを書く。

### 1-1. ログのフィールド（1行 = 1つの JSON）

| フィールド | 中身 | 備考 |
|-----------|------|------|
| `time` | 出した時刻（ISO 8601・UTC） | |
| `level` | ERROR／WARN／INFO／DEBUG | 本番は INFO 以上 |
| `msg` | 短い説明 | 固定の文言にし、値は別のフィールドに入れる（検索しやすくするため） |
| `event` | 業務上の出来事の名前（例: `http.request`・`group.created`・`group.joined`・`video.url_issued`） | INFO のとき必ず付ける。`http.request` は要求ごとの1行（応答が決まった後に出す） |
| `context` | どの部品が出したか（`Http`・`Auth`・`Console` など。NestJS の Logger の名前） | 実装で足した（調べるとき部品で絞れる） |
| `requestId` | 1回の要求を追うための ID（1-2） | 要求の処理中に出す行には全部付ける（起動時など、要求の外の行には付かない） |
| `userId` | 本人を特定できる値（`users.id`）だけ | メールアドレス・表示名は出さない |
| `method` / `route` | HTTP メソッドと**パスの型**（例: `/invitations/:token`） | 実際のパスでなく型を出す（1-3）。例外: `/api/auth/*` は NestJS のルートでないので、クエリを除いた実際のパス（値は入らない）。どのルートにも当たらなければ `(unmatched)` |
| `status` | HTTP ステータス | |
| `durationMs` | 処理時間（ミリ秒） | 保存の 1秒の目標を後から調べられる |
| `code` | design.md 5章のエラーコード（`GROUP_FULL` など） | エラー・WARN のとき |
| `err` | ERROR のときだけ、エラーの種類とスタックトレース | 応答には出さず、ログにだけ残す（design.md の 500 の決まり） |

### 1-2. リクエスト ID の付け方（仮置き）

- 要求が来たら、NestJS の入口（共通の処理）で ID を1つ決め、その要求の全ログに付ける（途中の関数に引数で渡し回さず、要求ごとの入れ物に持たせる）
- 決め方: 要求に `X-Request-Id` があり、形が正しければそれを使い、なければ UUID を作る。**応答にも同じ `X-Request-Id` を付ける**（利用者から「この時刻に失敗した」と聞くより、画面に出した ID を教えてもらう方が早く辿れるため）
- 作り方の候補: ① 自分で UUID を作る ② Lambda の呼び出し ID を使う。Lambda の呼び出し ID は AWS 側のログと結びつけやすいが、呼び出し口（infrastructure.md が決める）によって取り方が変わるため、**どちらにするかは未決**
- 画面からの要求（オフライン再送を含む）では、再送しても同じ ID を使うか別 ID にするかを、02-1 で決める（再送の追跡には「記録の `id`」を `event` のログに出す方が確実。これも未決）

### 1-3. ログに出さないもの

| 出さないもの | 理由・代わりに出すもの |
|--------------|-------------------------|
| パスワード・パスワードの変換後の値 | 漏れると不正ログインになる |
| Cookie・`Set-Cookie`・`Authorization`・セッションの値 | 他人になりすませる |
| **招待リンクの値**（パスに入っている `/invitations/{token}`） | 知っていれば参加できる。`route` は型（`:token`）だけを出す |
| **署名付き URL**（`?X-Amz-Signature=…` を含む全体） | 期限内なら誰でも動画を見られる。出すのは `event`（`video.url_issued`）と `videoId` だけ |
| メールアドレス | 個人情報。`userId` で足りる |
| **位置情報（GPX のルート・座標）** | 走った場所は住まいを推測できる。出すのは点の数・距離だけ |
| コメントの本文・表示名・グループ名 | 利用者が自由に書ける個人情報。長さだけ出す |
| リクエストの本文・クエリ文字列の全体 | 上のどれかが混ざる。必要な項目だけ選んで出す（全部を出して消す方式にしない） |
| 接続文字列・署名鍵（`DATABASE_URL`・better-auth の秘密の値） | 環境変数で渡し、起動時のログにも出さない |

**確かめ方:** design.md 6章の「ログの出力をテストで検査する」を、上の表の値を入れて実行し、出力に含まれないことを確かめる結合テストにする（testing-design.md の 3 章に、機能の PR で足す）。

### 1-4. 保存先と保存期間

Lambda の標準出力は CloudWatch Logs に入る。保存期間は**無期限が既定なので、有効期限を必ず設定する**（費用が静かに増えるのを防ぐため）。値は **30日（仮置き）**。設定は infrastructure.md の構築手順に入れる。

### 2-2. 見る項目（案）

| 項目 | 何を見るか | 注意の目安（仮置き） | 費用 |
|------|-----------|----------------------|------|
| Lambda の失敗数（`Errors`） | API の想定外の失敗 | 5分間に1回以上が続くとき | 無料枠の範囲（アラーム1個） |
| Lambda の実行時間（`Duration`） | 遅くなっていないか | 保存の目標 1秒に対し、平均が数秒を超えるとき | 同上 |

| `/health`（生きているかの確認・DB に触れない） | 画面と API の入口が生きているか | 外部の死活監視サービスや定期実行で呼ぶ案があるが、外部サービスの追加なので**未決・本人確認が必要** | 未確認 |
| Neon の使用量 | 計算時間・ストレージが無料枠に近づいていないか | Neon の管理画面で月に1回見る（自動の通知は作らない） | 無料 |

| 動画・GPX の S3 の容量 | 肥大化していないか | 月に1回、S3 の使用量を見る | S3 の単価は**未確認・本人確認が必要** |

## 3. 障害対応の流れ

```
気づく → 切り分ける（最初に見る場所） → 対応する → 直ったか確かめる → 記録する
```

1. **気づく:** 利用者（仲間）からの連絡、または週に1回の CloudWatch の確認
2. **切り分ける:** 下の表の順に、**画面 → 入口（CloudFront）→ API（Lambda）→ DB（Neon）**と奥へ進む。いつ・誰が・どの操作かを聞き、`requestId`（応答の `X-Request-Id`）や `userId` でログを探す
3. **対応する:** 原因別。アプリの不具合は直して出し直す。DB の不具合は4章
4. **確かめる:** 同じ操作をもう一度して成功すること。ログに同じエラーが続いていないこと
5. **記録する:** 原因・対応・再発防止を残す。ログに情報が足りなかったときは、1章を直す

### 想定する障害

| 症状 | 最初に見る場所 | 切り分けの順番 | よくある原因の仮説 |
|------|----------------|----------------|-------------------|
| **画面が開かない** | ブラウザの別の通信（他のサイトは見られるか）→ 画面のURLの応答（CloudFront） | ① 利用者の通信 ② CloudFront の応答（4xx／5xx） ③ 画面のファイル（S3）が置かれているか ④ 直近のデプロイ | 配信の更新に失敗した・ファイルの置き忘れ・Service Worker が古い画面を出している（F-30 の③。仮置き） |
| **ログインできない** | `/api/auth/*` の応答のステータスとログ（`event`／`code`） | ① パスワードの間違い（正しい文言か）② 401 か 5xx か ③ Cookie が付いているか（同じサイトで配っているか）④ DB につながるか | セッションの期限・Cookie の設定（`Secure`・`SameSite`）・DB の自動停止からの起動待ち |
| **記録が保存されない** | 画面の上部の帯（「送信待ち N件」）→ API の応答（`POST /records`・`/sets`）のステータス | ① 帯が出ているか（電波なし／ログイン切れなら記録は端末に残る）② 400（入力の範囲）③ 401 ④ 5xx（Lambda のエラー・DB）⑤ 同じ `id` の再送で 200 になっているか（二重ではなく成功） | 送信待ちの扱いは次のとおり（2026-10-28 決定。作成系はすべて冪等なので、再送しても二重にならない）。**5xx・408・429・ネットワーク断**は送信待ちに残して、間隔を空けて再送する（帯に「送信待ち N件」を出し続ける）。**400・403・409** は再送しても直らないので、送信待ちから外して「送れなかった記録」として1回だけ知らせる。**401** は保持する（ログインし直せば送れる）。**404** は親の記録がまだ届いていない順序ずれの可能性があるので、同じ順番の列の中で親が成功するまで待つ。つまり 5xx が続いても記録は端末に残る。それでも最初に「記録が失われたか」を確かめる |
| **動画が見られない** | `GET /videos/{id}/url` の応答（403／404／5xx） | ① 仲間が見ているなら期限（`visible_until`。日曜 24:00 日本時間）を過ぎていないか ② 他グループの記録ではないか（404）③ 署名付き URL の有効期限切れ（5分）④ 置いた動画の形式がブラウザで再生できるか（iPhone の Safari。リスク #2）⑤ S3 に置けているか | 期限切れは仕様どおり（障害ではない）。再生できない形式は撮影形式の問題 |

どの障害でも、**記録のデータが失われていないか**を最優先で確かめる。直す前に、現状（エラーの内容・影響を受けた人・時刻）を書き残してから手を入れる。

## 4. バックアップと復旧

### 4-1. データベース（Neon）

確認した日: **2026-10-28**。出典: [Neon の料金プラン](https://neon.com/docs/introduction/plans)・[ブランチの復元](https://neon.com/docs/introduction/branch-restore)

| 項目 | 確かめられたこと |
|------|------------------|
| 戻せる期間（Free） | **6時間**（変更履歴の上限 1GB-月。追加料金なし） |
| 何ができるか | 過去の時点（時刻）を指定して、ブランチを**その時点に戻す**（復元） |
| 復元の影響 | **今のデータは上書きされる**（データベースの中身とスキーマ全体が戻る）。ただし、復元の前の状態は自動で「バックアップのブランチ」（名前は `{ブランチ名}_old_{時刻}`）として残る |
| 子ブランチ | 子のブランチは、この復元の対象にならない |

**分かること:** 6時間より前の状態には、Neon の標準の機能では戻せない。つまり、**一昨日の誤操作は戻せない**。

**未確認:** 履歴の期間を超えたあとの別の取り方（定期的なダンプなど）。これは外部への書き出しやストレージを伴い、費用と運用が増えるため、「少人数・無料枠」の方針と釣り合うかを**本人と相談してから決める（未決・本人確認が必要）**。今は決めない。

### 4-2. 復旧の手順（案）

1. 何が起きたかを書き留める（時刻・影響範囲）。**書き込みを増やさない**（アプリを止められるなら止める。止め方は未決）
2. Neon の管理画面で、戻したい時刻（問題の直前）を決める。**6時間以内であること**を確認する
3. 復元を実行する前に、**今の状態も残る**（バックアップのブランチができる）ことを確認する。**元に戻せない操作として、実行は本人に確認してから**行う
4. 復元後、アプリが動くことと、データが戻っていることを確かめる。復元の時刻より後に作られた記録は失われる。オフラインで送信待ちの記録は、つながったときに再送されるので、冪等（同じ `id` は1件）のおかげで二重にならない

### 4-3. 画面・API・ファイル

| 対象 | 復旧の考え方 |
|------|--------------|
| 画面・API のコード | Git が正本。直前の版を出し直す（デプロイ手順は infrastructure.md） |
| S3 の動画・GPX | 消えた場合の復旧は**未確認**（S3 のバージョニングの要否・費用を確かめていない）。動画は「その週だけ仲間に見える」性質のもので、失っても記録（`records`・`workout_sets`）は残る |
| 設定・秘密の値 | リポジトリに入れない。再作成の手順を infrastructure.md に書く |

## 5. 運用の既知の制限

| 制限 | 内容・対応 |
|------|-----------|
| 少人数前提 | 最大5人のグループ。大人数の負荷・同時アクセスは想定しない。負荷試験は後（testing-design.md の 5 章） |
| 無料枠 | Neon Free（ストレージ 1GB・計算 100 CU 時間／月・戻せるのは6時間）、CloudWatch（アラーム10個・ログ 5GB）の範囲で運用する。枠を超える可能性があるときは、有効にする前に本人に確認する |
| 最初の接続が遅い | Neon は5分の無操作で自動停止し、止められない。停止後の最初の要求は遅くなる。保存 1秒の目標に影響しうる（testing-design.md の 5 章で測る） |
| オフラインの7日ルール | iPhone の Safari は、操作しないまま7日使うと端末内の保存（IndexedDB・Service Worker）を消す。7日以上開かずに Safari で使い続けると、送っていない記録は消える。ホーム画面に追加したアプリは対象外（tech-stack.md） |
| 5xx のときの扱い | 送れなかった記録をどうするかは**未決**（02 の計画で決める）。決まったら3章の表を直す |
| 監視の通知 | 自動の通知は未決。当面は週1回の目視 |
| 復旧の範囲 | データベースは直近6時間まで。それより前は戻せない |
| 退会 | 作らない（features.md）。個人情報の削除の依頼は、手作業で対応する（手順は提出後に検討） |
| 位置情報 | GPX のルートは走った場所を示すため、ログに出さない（1-3）。仲間への見え方は features.md の範囲 |
